# 02 - 技术选型

> **TL;DR**：全部决策结论先行——**D1 UI 框架：Flutter**（P0 三端一套代码，P1 全部可达，阅读器生态最完整）；**D2 渲染：txt/md/epub 走纯 Flutter 自渲染管线（epub 解析用 epub_pro/epubx 系，md 用 flutter_markdown_plus），pdf 用 pdfrx（pdfium，六端可用）**，不引入 WebView 依赖（官方 webview_flutter 不支持 Windows）；**D3 本地存储：drift（SQLite）管理元数据/进度/同步状态 + 文件系统存正文**；**D4 元数据：每本书一个 JSON 文件 + `schemaVersion` 字段，云端目录布局对坚果云与通用 WebDAV 一致**（详细 schema 见 [05](./05-元数据Schema与云端目录布局.md)）；**D5 冲突：元数据整体 LWW（`updatedAt` + `deviceId` 决胜）+ 单调 `rev` 乐观锁 + tombstone 删除标记**（详细规则见 [04 §6](./04-同步引擎与冲突解决.md)）。每项决策均给出 ≥2 候选对比、推荐理由与风险。

## D1. 跨平台 UI 框架

需求约束：P0 = Android（手机+平板）+ Windows；P1 = iPad/macOS/Linux 必须可达；免费开源；要能产出可安装的 app。

### D1.1 候选对比

| 维度 | **Flutter** | React Native（+react-native-windows） | Kotlin Multiplatform + Compose Multiplatform | Tauri 2 | Electron |
| --- | --- | --- | --- | --- | --- |
| Android | ✅ 一等公民 | ✅ 一等公民 | ✅ 一等公民 | ✅（2.x 支持，生态较新） | ❌ 无官方方案（需另配 Capacitor 等，实际两套栈） |
| Windows | ✅ 官方稳定支持 | ⚠️ react-native-windows 可用但明显滞后于主线，社区维护 | ⚠️ Compose for Desktop 基于 JVM，可用但 Windows 观感与打包体积一般 | ✅ 支持，WebView2 | ✅ 最成熟 |
| P1: iPad | ✅ 官方稳定 | ✅ 官方稳定 | ✅（Compose iOS 已稳定，但生态新） | ⚠️ 支持但成熟度最低 | ❌ 无 |
| P1: macOS / Linux | ✅ 官方稳定 | macOS ✅ / Linux ⚠️ 社区 | ✅ | ✅ | ✅ |
| 渲染一致性 | 自绘引擎，四端像素级一致 | 原生控件映射，三端观感/行为差异大 | 原生控件映射，差异大 | 各端系统 WebView，差异大 | Chromium，一致但重 |
| 阅读器相关生态 | 最丰富：epub/pdf/markdown 库齐全（见 §D2） | epub 生态弱（epubjs 需 WebView 套壳）；pdf 依赖原生库桥接 | 几乎无现成阅读库，多数需桥接原生 | 依赖 Web 生态（epub.js/pdf.js 可用），但移动端桥接层薄 | Web 生态全套可用 |
| 自绘文本排版能力（分页必需：TextPainter 级测量） | ✅ 原生支持，成熟 | ⚠️ 需依赖原生 Text 组件，逐字符测量成本高 | ⚠️ 同左 | ⚠️ 在 WebView 内排版，宿主不可控 | 同 Tauri |
| 包体积 | 中（空 app ≈ 8-15MB，含 pdfium 后 ≈ 30-50MB/ABI） | 中 | 中 | 小（≈ 10MB 级） | 大（≈ 100MB+） |
| 内存占用 | 中低 | 中 | 中 | 低 | 高 |
| 单代码占比 | P0 三端 ≈ 100% 共用 | ≈ 90%（Windows 侧常有平台分支） | ≈ 80-90%（iOS/桌面需适配） | 前端共用，移动端配置多 | 桌面共用，无移动 |
| 免费/开源 | ✅ MIT | ✅ MIT | ✅ Apache-2.0 | ✅ MIT | ✅ MIT |
| 主要风险 | Windows 桌面第三方插件成熟度参差；文本渲染中文度量需真机验证 | Windows 版维护节奏不可控；自定义排版几乎不可行 | 生态最年轻，阅读库需全部自研或桥接 | 移动端发布链与插件生态不够稳；后台任务受 WebView 进程模型约束 | 无移动端，直接排除 |

### D1.2 结论

**推荐 Flutter。** 理由：

1. P0 三端（Android/Windows）+ P1 三端全部为官方稳定支持目标，构建链均为官方维护（Android: Gradle；Windows: CMake+VS；iOS/macOS: Xcode；Linux: CMake+GTK），P1 可达性无技术障碍；
2. 电子书阅读器的两大核心自研点——**txt/epub 重排分页（需要 TextPainter 级文本测量）** 与 **统一观感的自绘主题**——恰是 Flutter 自绘引擎的强项，RN/KMP 在这点上明显吃亏（原生 Text 组件难以做逐段测量分页）；
3. 渲染生态最完整（§D2 逐格式给出可用库），四格式都有纯 Flutter 可用方案，不依赖 WebView；
4. Dart 单语言贯穿客户端 + 同步核心（sync_core 纯 Dart 包），无第二套语言栈。

**排除说明**：Electron 因无移动端直接出局；Tauri 2 作为"轻量备选"保留在观察名单，但其移动端（Android）发布链与插件生态成熟度不足 P0 要求，且 WebView 内分页使进度定位（locator）精度受各端 WebView 实现差异影响，与"跨设备精确恢复进度"目标冲突。

**风险与缓解**：

- *R1*：部分桌面插件（窗口管理、文件关联）社区维护 → 只选高星活跃插件（window_manager、file_picker），并在实现阶段做插件可用性验证；
- *R2*：中文字体度量差异导致分页在不同设备漂移 → 分页以"设备本地排版结果"为准，进度 locator 记录**逻辑位置**（章节+字符偏移）而非物理页码（见 [05 §4](./05-元数据Schema与云端目录布局.md)），从机制上免疫排版差异。

## D2. 四种格式的渲染方案

### D2.0 总原则与扩展点

所有格式经统一的 `BookFormatHandler` 接口接入（接口定义见 [03 §4.2](./03-系统架构设计.md)），渲染器彼此独立、按格式注册。新增格式（mobi/azw3）= 新增一个 Handler 实现 + 注册表登记，**不改动阅读器框架与同步引擎**（同步层只认 `contentHash` 与 `format` 字符串，格式无关）。

关键前置事实（调研核实）：

- 官方 `webview_flutter` **不支持 Windows**（官方 issue #96335 明确不在路线图），Windows 上 WebView 需 `webview_windows`/`flutter_inappwebview` 等第三方包 → 本项目**优先纯 Flutter 渲染，WebView 仅作兜底**；
- `flutter_markdown` 官方已于 2025-02 停维，社区后继 `flutter_markdown_plus` 维护中；
- `epubx`/`epub_view` 维护状态差；`epub_pro` 为维护中的解析 fork；
- `pdfrx`（pdfium）支持 Android/iOS/Windows/macOS/Linux/Web 六端，Apache-2.0。

### D2.1 EPUB

| 方案 | 思路 | Android | Windows | P1 可达性 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. 纯 Flutter 自渲染（推荐）** | `epub_pro`（或 `epubx`）解析 zip+OPF → 提取 spine/chapter HTML → `flutter_widget_from_html_core` 渲染富文本 → 自研分页引擎（TextPainter 按段落流测量切屏） | ✅ | ✅ | ✅ 六端同构 | 无 WebView 依赖、主题/字号/分页完全可控、locator 精确到字符偏移 | 分页引擎需自研（项目最大技术投入点）；复杂 CSS/表格渲染降级 |
| B. WebView + epub.js / foliate-js | 各端 WebView 里跑成熟 JS 渲染器，CFI 定位 | ✅ | ⚠️ 需第三方 WebView2 包（webview_windows 或 flutter_inappwebview） | Linux 缺系统 WebView 时不可用 | 分页/CFI 开箱即用，复杂 epub 兼容性最好 | Windows 依赖第三方 WebView 包；三端 WebView 行为差异导致 locator 精度不一致；内存高；进度定位受 WebView 内部实现黑盒影响 |
| C. flutter_epub_viewer（epub.js + inappwebview 封装） | 社区封装方案 B | ✅ | ⚠️ 同 B（其 Windows 支持跟随 flutter_inappwebview） | 同 B | 接入最快 | 同 B，且封装层本身维护一般 |

**推荐 A**，并把 B 列为**风险兜底**：`BookFormatHandler` 接口天然允许未来给 epub 注册第二个 WebView 渲染器作为"复杂书籍兼容模式"（见 [07-R6](./07-风险与待确认问题.md)）。分页引擎的降级策略：若按屏分页验证成本过高，v1 先交付滚动模式 + ratio 进度（locator 仍记录章节+字符偏移，不依赖分页），分页模式可后置——该降级不影响同步正确性。

### D2.2 PDF

| 方案 | 思路 | Android | Windows | P1 可达性 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. pdfrx（推荐）** | pdfium 原生渲染，自带 Viewer 组件（缩放/跳转/缩略图/搜索） | ✅ | ✅（自动带 pdfium 二进制） | ✅ 六端 | 六端一致、功能全、Apache-2.0、活跃维护 | 包体 +6-10MB/ABI（pdfium）；Linux 需系统依赖 |
| B. pdfx | pdfium 渲染 + 自绘查看器 | ✅ | ⚠️ 支持 | ⚠️ | 纯渲染 API 灵活 | 查看器功能（手势/滚动）需自研，工作量大 |
| C. WebView + pdf.js | JS 渲染 | ✅ | ⚠️ | ⚠️ | — | 同 epub 方案 B 的 WebView 缺陷，且大文件性能差 |

**推荐 A（pdfrx）**。进度 locator 直接用页码 + 页内纵向比例（`pageIndex + yRatio`），与渲染库解耦。

### D2.3 Markdown

| 方案 | 思路 | 平台 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **A. flutter_markdown_plus（推荐）** | 官方 flutter_markdown 的维护中社区 fork，纯 widget 渲染 GFM | 六端 | 纯 Flutter、样式可定制、与主题系统集成 | fork 长期维护不确定（登记 [07-R7](./07-风险与待确认问题.md)；必要时 fork 收编进仓库） |
| B. markdown 解析 + flutter_widget_from_html | `markdown` 包转 HTML → HTML 渲染组件 | 六端 | 渲染组件与 epub 共用 | 多一层转换，样式控制绕一道 |
| C. WebView + markdown-it | JS 渲染 | 缺 Windows 官方 WebView | — | 同上各 WebView 缺陷 |

**推荐 A**，代码块高亮用 `highlight` 系包；按标题层级（h1/h2）切"章节"供目录与 locator 定位（`blockIndex + charOffset`）。

### D2.4 TXT

| 方案 | 思路 | 平台 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **A. 自研管线（推荐）** | 编码检测（`charset_detector` + Android `charset_converter` 兜底）→ 解码 → 章节切分（正则规则："第X章/卷/回/节"、序号模式，可配置）→ TextPainter 分页 | 六端 | 中文 txt 场景完全可控，GBK 老书可读，locator = `chapterIndex + charOffset` 精确 | 章节识别对无规则文本退化为全文单章（可接受） |
| B. WebView + 自定义 JS | JS 里分页 | ⚠️ | — | 编码检测/大文件流式处理在 JS 侧更弱 |

**推荐 A**。大文件（>20MB txt）采用流式解析 + 章节偏移索引（导入时一次性建索引存 SQLite，阅读时按需解码章节片段），避免整本驻留内存。

### D2.5 格式扩展机制（预留 mobi/azw3 等）

1. 新格式实现 `BookFormatHandler`（detect / parse 元数据 / buildToc / buildRenderer / locator 编解码）；
2. 在 `FormatRegistry` 注册（扩展名 + 魔数双通道识别）；
3. 同步层零改动：元数据 `format` 是自由字符串，正文是原样字节文件，`contentHash` 格式无关；
4. locator 兼容：`progress.locator` 内含 `type` 判别字段，未知 type 的进度按"整本 percent"降级恢复（见 [05 §3.3](./05-元数据Schema与云端目录布局.md)）。

## D3. 本地存储方案

需求：书籍文件、元数据、阅读进度、同步状态；单机 2000 本规模；需要增量/条件更新与索引查询。

### D3.1 候选对比（元数据/进度/同步状态的结构化存储）

| 维度 | **drift（SQLite）** | Isar 3 | Hive | ObjectBox |
| --- | --- | --- | --- | --- |
| 数据模型 | 关系表 + SQL，复杂查询/排序/索引最强 | NoSQL 文档，索引可用 | Key-Value / 对象盒 | NoSQL 对象 |
| 多条件书库查询（搜索/排序/过滤） | ✅ SQL 原生 | ⚠️ filter API | ❌ 需全量内存过滤 | ⚠️ 条件查询弱于 SQL |
| 事务与崩溃一致性 | ✅ WAL，久经验证 | ✅ | ⚠️ 弱 | ✅ |
| 六端可用性 | ✅（全平台） | ⚠️ 桌面端曾长期 beta，维护节奏波动 | ✅（v4 母公司变动，维护不确定性） | ⚠️ 桌面/移动可用，FFI 维护一般 |
| 纯 Dart 可测试性 | ✅（可跑内存实例 + 生成代码） | ✅ | ✅ | ✅ |
| 维护活跃度 | 高（社区标准件） | 中，曾停滞后恢复 | 中低 | 中 |
| 迁移工具 | ✅ schema 版本化迁移链 | 有 | 弱 | 有 |

### D3.2 结论

**推荐 drift（SQLite）**，理由：书库管理本质是"多条件关系查询"（搜索/排序/分组/同步状态过滤），SQL 是最自然表达；drift 生成类型安全代码、支持内存实例做单元测试、六端无坑；SQLite 文件本身也便于未来导出/诊断。

**存储分工**（详细 DDL 见 [05 §5](./05-元数据Schema与云端目录布局.md)）：

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 书籍文件（原样字节） | 应用文档目录 `files/books/{bookId}/{原文件名}` | 不改写原始文件；pathfinder 记录在 DB |
| 封面图 | `files/covers/{bookId}.webp` | 可随时重建 |
| 元数据/进度/同步状态/待同步队列 | drift（SQLite，WAL 模式） | 单一事实源 |
| 排版与阅读偏好 | drift 的 settings 表 | 仅本地（FR-206） |
| 凭据 | flutter_secure_storage（Keystore / DPAPI / Keychain / libsecret） | 绝不入 SQLite（NFR-03） |

**风险**：drift 生成代码与 Dart SDK 版本耦合 → 锁定 build_runner 版本矩阵；CI 移除后（[07-A19](./07-风险与待确认问题.md)）改为**本机**跑生成检查（`dart run build_runner build --delete-conflicting-outputs` 后 `git diff --exit-code` 校验生成物未漂移）。

## D4. 元数据文件格式与云端目录布局

### D4.1 候选对比

| 维度 | **每书一个 JSON 文件（推荐）** | 全库单一 index.json | SQLite 数据库文件放云端 |
| --- | --- | --- | --- |
| 增量粒度 | ✅ 单书级（哪本变了拉哪个，ETag 天然适配） | ❌ 任何一本书变化都要重传整个索引 | 单书级（WAL） |
| 并发写冲突面 | ✅ 冲突仅发生在单书 JSON 内，LWW 范围小 | ❌ 全库文件级冲突，LWW 会丢其他书的更新 | ❌ 二进制合并几乎不可行，需锁或单写者 |
| WebDAV 友好度 | ✅ PUT/GET 原子、PROPFIND 列目录 + ETag 即增量清单 | ⚠️ 大 JSON 每次全量上传 | ❌ 需下载整个库文件并上传，流量放大 |
| 可读性/可修复性 | ✅ 人可读、单文件损坏不影响全库 | ⚠️ 单点损坏全库不可读 | ❌ 不可读 |
| 2000 本规模元数据总量 | ≈ 2-8MB（每本 1-4KB） | 同左但传输放大 | 更大 |

### D4.2 结论

**推荐"每书一个 JSON 文件"**，外加一个极小的 `library.json`（库级常量：`schemaVersion`、`libraryId`、创建时间，几乎不变）。目录布局对 **坚果云与通用 WebDAV 完全一致**：

```
{同步根目录}/
├── library.json            # 库描述：{schemaVersion, libraryId, createdAt}
├── meta/{bookId}.json      # 每书元数据（含进度、书信息、hash、删除标记）
├── books/{bookId}.{ext}    # 正文文件，文件名 = bookId + 原扩展名
└── tmp/                    # 上传临时区（.part → MOVE 原子提交）
```

`schemaVersion` 字段存在于 `library.json` 与每个 `meta/*.json` 顶层，演进规则（只加字段、不删字段、读取方容忍未知字段）与迁移矩阵见 [05 §6](./05-元数据Schema与云端目录布局.md)。完整字段定义、locator 子 schema、本地 SQLite 表与云端 JSON 的映射同样见 [05](./05-元数据Schema与云端目录布局.md)——本文不再重复。

## D5. 冲突解决策略

需求：多设备同时修改阅读进度；元数据除进度外还有阅读时长等累积字段；"一端删除、另一端在阅读"的删除冲突。完整规则与时序在 [04 §6-§7](./04-同步引擎与冲突解决.md)，此处记录选型对比。

### D5.1 候选对比

| 维度 | 纯时间戳 LWW | **LWW + 单调 rev + deviceId 决胜（推荐）** | 最远进度优先（max-progress） | CRDT / 向量时钟 |
| --- | --- | --- | --- | --- |
| 实现复杂度 | 极低 | 低 | 中（"最远"需要坐标可比较，跨格式跨排版时并不可靠） | 高 |
| 时钟回拨/偏差容忍 | ❌ 回拨直接丢更新 | ✅ rev 单调递增（本地持久计数器）兜底，时间戳仅展示与决胜辅助 | ⚠️ 不受时钟影响 | ✅ |
| 累积字段（阅读时长） | ❌ 直接覆盖会丢另一端时长 | ⚠️ 默认覆盖；对 `totalSeconds` 采用**字段级求和合并**特例 | 同左 | ✅ 但过度设计 |
| 删除 vs 修改冲突 | 需额外规则 | ✅ tombstone 带 `deletedAt`，与进度更新走同一 LWW 序 | 需额外规则 | ✅ |
| 用户心智 | "以后读的为准"（符合直觉） | 同左 | "读得最多的为准"（看似合理，实则用户可能有意回看重读，"最远"未必是用户意图；且跨格式坐标不可比） | 需要用户理解合并结果 |
| 可预测性 | 高 | 高 | 中 | 低（结果难预期） |

### D5.2 结论

**推荐"LWW + 单调 rev + deviceId 决胜"**，规则一句话：**每本书的元数据以 `(rev, updatedAt, deviceId)` 三元组定序，大者胜；`rev` 由写端基于本地持久计数器单调递增，`updatedAt` 为毫秒时间戳，`rev` 相同时再比时间戳、再比 deviceId 字典序**。特例：`reading.totalSeconds` 采用"两端求和"合并（见 [04 §6.3](./04-同步引擎与冲突解决.md)）。

理由：阅读进度冲突的本质是"用户接受任意一个合理结果，但绝不能丢书、丢进度、出现不可预测行为"。LWW 心智最简单、结果可预期；rev 单调性消除了时钟回拨这一 LWW 唯一致命弱点；CRDT 对单人书库场景是过度设计。放弃"最远进度优先"的原因：跨格式（pdf 页码 vs epub 字符偏移）无法可靠比较"更远"，且重读场景下"最远"违背用户意图。

**风险**：极端时钟偏差（>24h）时用户可能觉得"我刚读的没生效" → 设置页提供"以本设备为准"强制覆盖按钮（FR-406 的兜底操作），并登记 [07-R8](./07-风险与待确认问题.md)。

## D6. 客户端工程配套选型（补充决策）

| 用途 | 选型 | 备选与理由 |
| --- | --- | --- |
| 状态管理 | **Riverpod** | Bloc（样板多）/ Provider（停止演进）/ GetX（质量争议） |
| 路由 | **go_router** | 声明式、深链友好，官方维护 |
| HTTP 客户端 | **dio** | 拦截器生态（重试/日志/认证刷新）成熟；WebDAV 客户端基于 dio 自研薄封装（PROPFIND/PUT/MOVE 等，Dart 无维护良好的通用 WebDAV 库，自研 ≈ 300 行 XML 拼装 + 解析） |
| 安全存储 | **flutter_secure_storage** | Android Keystore / Windows DPAPI / iOS-Keychain / libsecret，六端覆盖 |
| 文件选择 | **file_picker** | 桌面+移动统一 API |
| 后台任务 | **workmanager**（Android）；桌面端用进程内定时器 + 启动/恢复触发 | 桌面 OS 级后台任务无统一方案，且阅读类应用前台时长占比高，可接受（记录 [07-A10](./07-风险与待确认问题.md)） |
| 日志 | **talker**（或 logger） | 结构化、可导出 |
| ID 生成 | **ulid** | bookId/deviceId 用 ULID：时间有序 + 无需协调 |
| 哈希 | **crypto**（SHA-256 流式） | 大文件流式计算，不驻留内存 |
